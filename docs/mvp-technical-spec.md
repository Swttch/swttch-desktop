> 작성일: 2026-10-08 (한국 시간)
> 상태: 소스 확인에 기반한 설계 초안. 정책·API 계약 미확정, 구현 전.
> 제품 요구사항: [MVP PRD](mvp-prd.md)

## 책임 경계

2026-10-08 추가 확정: [핵심 원칙](core-principles.md)에 따라 Electron과 localhost 브라우저가 같은 React + TypeScript 셸 및 공통 로컬 API를 사용한다. 아래 초기 설계의 Electron 셸 책임 중 프로젝트·상태·데이터 기능은 공통 Node.js 서비스에 두고, 창·네이티브 기능만 호스트 어댑터에 둔다.
현재 구현은 `src/local-service.cjs`의 공통 HTTP API와 원본 백엔드 프록시를 사용한다. Electron은 `src/host.cjs`를 별도 Node 프로세스로 실행하고 같은 React 셸을 로드한다. preload에는 네이티브 폴더 선택만 남긴다. 일반 프론트 검증은 Codex 브라우저에서 수행한다.
아래 부트스트랩·데이터·인증 항목은 초기 초안이며, 실제 개발 실행 구조와 검증 범위는 README를 우선한다. 필수 앱 로그인과 중앙 API는 아직 미구현이다.

| 구성 | 책임 |
|---|---|
| Electron 셸 | 창, 단일 패널·탭, 네이티브 폴더 선택, 로컬 백엔드 프로세스 관리 |
| 기존 채팅 웹앱 | 세션 선택·메시지·스트리밍·권한·diff 등 기존 채팅 UX |
| 로컬 Node.js 백엔드 | Agent CLI, 세션·파일·설정 I/O, 데스크탑 메타데이터, 중앙 API 연동 |
| 중앙 API | 앱 계정과 라이선스, PostgreSQL |

Electron 메인에 CLI·세션 비즈니스 로직을 복제하지 않는다. 중앙 API 호출 주체는 로컬 백엔드로 두는 안을 제안한다.
앱 인증 비밀의 OS 보관소 접근은 셸 어댑터로 제공하는 안을 검토하며, 공급자·Electron API·Linux 지원 조건 확인 후 확정한다.

## 현재 소스에서 확인한 재사용 지점

경로는 상위 플러그인 저장소 기준이다. 실제 Electron 실행은 아직 검증하지 않았다.

| 소스 | 확인한 계약 | 설계에 주는 영향 |
|---|---|---|
| `scripts/build.sh`의 `standalone-tgz` | backend.mjs·account-cli.mjs·Windows 보조 스크립트·vendor·webview를 tgz에 포함 | 기존 산출물 이름과 구성 보존 |
| `backend/src/config/environment.ts` | `PORT`, `CCG_BIND`, `WEBVIEW_DIR`, `CCG_AUTH_TOKEN`, 종료코드 75 | 전용 포트·loopback·정적 파일 경로·로컬 인증 주입 |
| `backend/src/server.ts` | stdout `PORT:<port>` 및 `CCG_INITIAL_PAIR_CODE` 초기 페어링 | 준비 신호를 읽고 일회용 코드로 페이지 연결 |
| `webview/src/api/bridge/WebSocketConnector.ts` | 동일 origin의 `/ws`, 페어링 후 인증, 재연결 | 기존 웹앱을 백엔드 HTTP origin에서 로드 |
| `backend/src/core/parent-watchdog.ts` | `CCG_HOST_PID`로 실제 호스트 감시 | Electron 런처 PID 전달 검토 |
| `backend/src/core/entities/entityPaths.ts` | 엔티티 루트에 `CCG_HOME` 지원 | 일부 저장 경로에만 적용됨을 전제로 감사 필요 |
| `backend/src/core/features/profile.ts` | `~/.claude-code-gui/profile.json` 직접 사용 | `CCG_HOME`만으로 전체 데이터 분리가 되지 않음 |
| `backend/src/core/handlers/sponsorAccount.ts` | 후원 키 기반 기존 계정 기능 | 앱 사용자 로그인 계약으로 그대로 대체 불가 |

## 로컬 런타임 부트스트랩 제안

1. 셸이 앱 데이터 경로와 런타임 산출물 존재 여부를 확인한다.
2. 별도 Node 프로세스로 기존 backend.mjs를 실행한다. Electron 자체 프로세스를 Node로 사용하는 방식과 별도 런타임 번들은 호환성 실측 후 선택한다.
3. `PORT=0`, `CCG_BIND=127.0.0.1`, `WEBVIEW_DIR` 및 호스트 PID를 명시한다. 실제 할당 포트는 stdout에서 읽는다.
4. 프로덕션 로컬 인증 토큰과 일회용 페어링 코드를 주입한다. 원문은 로그·문서에 남기지 않는다.
5. 준비 신호와 HTTP 응답을 확인한 뒤 단일 채팅 탭을 해당 origin의 `?pair=` URL로 연결한다.
6. 실제 WebSocket 연결과 프로젝트 컨텍스트 준비를 확인한다. HTTP 200만으로 채팅 준비 완료를 선언하지 않는다.

토큰의 영속 범위와 재시작 시 유지 방식은 복구 정책에 맞춰 확정한다. 종료코드 75와 비정상 종료는 별도로 취급한다.
기존 백엔드는 포트 충돌 시 기존 프로세스를 회수하는 경로가 있으므로 고정 기본 포트를 공유하지 않는 안을 제안한다.
idle shutdown·부모 감시·호스트 연결 감시가 Electron에서 어떻게 동작하는지도 첫 연결 검증에 포함한다.

## 인증 계약 결정 항목

필수 앱 로그인은 로컬 `/ws` 인증 및 Agent CLI 인증과 별개의 계약이다.
Google·GitHub·이메일을 모두 지원하고 기존 Swttch 계정을 재사용하는 요구는 2026-10-08 사용자가 확정했다.
`backend/src/core/features/license.ts`는 현재 후원 키 자체가 계정 식별자이며 별도 계정 로그인이 없다고 명시한다. 따라서 기존 사용자 재사용 요구를 충족하려면 실제 기존 계정 원천을 확인하고 새 앱 인증과의 연결 계약을 정해야 한다.
기존 계정이 후원 키 기반 사용자를 의미한다면, 로그인한 계정에 기존 라이선스 소유권을 연결하는 별도 절차가 필요하다. 이메일 문자열 일치만으로 소유권을 자동 이전하지 않는 안을 제안한다.
이메일 로그인은 비밀번호·매직 링크·일회용 코드 중 방식을 정해야 한다.
공급자가 정해지면 로그인 시작·콜백·인증 확인·갱신·로그아웃·라이선스 조회의 요청/응답과 오류 코드를 명세한다.
외부 브라우저 로그인 및 데스크탑 복귀 방식은 공급자에 맞춰 설계한다. 아직 임의의 엔드포인트를 구현하지 않는다.
렌더러에는 필요한 계정 표시 상태만 제공하고 중앙 인증 비밀을 노출하지 않는 안을 제안한다.
로그인 전 채팅 기능 제한은 셸 표시뿐 아니라 작업 시작을 처리하는 백엔드에서도 검증하는 안을 설계한다.

## 데이터 경계 제안

- `~/.swttch`에 데스크탑의 SQLite DB와 로그를 배치한다.
- SQLite의 최초 대상은 선택 프로젝트, 마지막 활성 탭 참조, 앱 데이터 스키마 버전으로 제안한다. 확정 후 테이블과 마이그레이션을 정의한다.
- CLI JSONL 및 세션 원본은 기존 저장 형태와 전달 구조를 유지한다.
- 인증 비밀은 일반 SQLite·설정 JSON에 평문 저장하지 않는 안을 검토한다.
- 기존 `~/.claude-code-gui` 데이터는 경로별로 조사하고 공유·분리·이관 정책을 정한다. 원본 이동이나 자동 마이그레이션은 아직 승인되지 않았다.
- 중앙 PostgreSQL에는 계정·라이선스만 둔다. 프로젝트·세션 동기화 스키마는 만들지 않는다.

## 패키징과 개발 경로

배포는 기존 standalone tgz를 의존 산출물로 소비하는 방향을 유지한다. tgz 버전·무결성·vendor 실행 권한을 확인한다.
개발 소스 연결은 상위 저장소의 빌드 산출물을 명시 경로로 참조하는 안을 제안한다. 배포 번들에 개발 절대 경로를 남기지 않는다.
상위 플러그인 코드를 수정할 때는 별도 worktree에서 작업하고, 데스크탑 자체 저장소와 변경을 구분한다.
데스크탑 실행·빌드·테스트는 package.json의 npm scripts를 사용한다. `npm run dev`는 Electron 개발환경, `npm start`는 일반 앱을 실행한다. 상위 CCG 런타임 빌드는 기존 공식 빌드 스크립트를 호출한다.
Electron 버전, 패키저, 서명·공증, npm 런처 및 Cask 업데이트는 배포 스펙에서 확정한다.

## 검증 순서

1. 런타임 호환: backend.mjs 실행, 정적 페이지·페어링·WebSocket·프로젝트 선택.
2. 실제 CLI 한 턴: 작업 폴더 일치, 스트리밍, 권한 승인·거부, 중단·완료.
3. 앱 인증: 첫 로그인·취소·실패·갱신·로그아웃·중앙 API 장애.
4. 종료·복구: 확정 정책에 따라 동일 탭을 유지한 장애 및 재연결 관찰, 앱 재실행, 자식 프로세스 정리.
5. 회귀 및 배포: JetBrains·standalone 보존, OS별 설치와 실행.

자동 백엔드 재시작 및 작업 자동 재개는 정책 확정 전 구현하지 않는다. 현재 문서는 기술 검증 결과나 출시 근거가 아니다.
